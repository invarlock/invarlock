# A Machine-Readable Schema for Weight-Edit Evaluation Reports with First-Class Verifier Traces

## Abstract

Evaluations of weight edits such as quantization and pruning increasingly mix
statistical guard frameworks (e.g., InvarLock), general evaluation harnesses,
and task-specific external verifiers (e.g., HumanEval/MBPP execution). Today
these tools emit incompatible artifacts, making it difficult to align guard
evidence with verifier outcomes, reproduce end-to-end verification loops, or
build automated promotion gates with auditable inputs. We propose a lightweight
JSON Schema for **verifier-carrying evaluation artifacts** that links three
elements in a single machine-checkable object: `guard_evidence` (tool-native
guard measurements, thresholds, and verdicts, including InvarLock evaluation
reports and optional `invarlock verify` outputs), `verifier_traces` (external
verifier results together with a trace contract covering prompt hashes, harness
and sandbox versions, resource limits, and decoding parameters), and
`provenance` (model, tokenizer, edit configuration, and tool versioning). A
companion `schema-verify` utility validates structural conformance and
cross-block consistency, enabling downstream automation to treat the artifact
as a reliable unit of evidence in verification-aware pipelines. We implement
serializers for InvarLock artifacts and code-execution verifiers and
demonstrate cross-tool queries on a paired dataset spanning multiple models and
edit families, including cases where guard evidence and verifier outcomes
disagree. We release the schema, serializers, validator, and a queryable demo
corpus as open-source building blocks for composing soft evidence with hard
verification in model-edit workflows.

## 1. Introduction

When a language model is quantized, pruned, or otherwise weight-edited,
evaluation evidence is produced at three layers that rarely interoperate:

1. **Guard frameworks** (e.g., InvarLock) emit diagnostic measurements and gate
   flags intended to detect harmful edits quickly.
1. **Evaluation harnesses** define prompt sets and generation parameters.
1. **External verifiers** (e.g., HumanEval / MBPP code-execution sandboxes)
   provide the decisive outcome signal: did the edited model’s outputs satisfy
   the verifier?

This three-layer structure aligns with VerifAI’s emphasis on putting
verifier-grounded outcomes at the center of evaluation. In practice, however,
the layers emit incompatible artifacts with missing provenance. Basic
comparability questions become hard to answer automatically:

- Are two pass@1 numbers computed over the same prompt set?
- Under the same harness revision and sandbox constraints?
- With the same decoding parameters and seed?

Existing formats do not close this gap. Model cards and leaderboards rarely
encode verifier determinism contracts. Dataset metadata schemas improve dataset
provenance but do not pin verifier-run provenance. Supply-chain frameworks
provide content-addressing primitives that inspire our design but target
software artifacts, not model-evaluation evidence.

We address this with a **verifier-carrying artifact**: a strict JSON Schema
that co-locates auxiliary guard evidence (an InvarLock evaluation report,
hash-linked) with first-class verifier traces under shared provenance. The
verifier trace’s contract pins comparability-critical conditions (prompt-set
digests, harness identity, model/tokenizer revisions, decoding parameters, and
execution sandbox limits). A `schema-verify` tool checks structural conformance
and contract-driven cross-block consistency, without claiming formal guarantees
about model correctness or verifier soundness.

**Contributions.**

- A **verifier trace** schema and contract that makes external verifier runs
  auditable via prompt-set digests, harness identity, model/tokenizer revision
  pins, decoding parameters, and sandbox bounds.
- A **verifier-carrying artifact** wrapper schema that packages auxiliary guard
  evidence (hash-linked InvarLock evaluation reports and optional verify output)
  together with first-class verifier traces in one queryable object.
- A lightweight **schema validator** (`schema-verify`) that checks JSON Schema
  conformance and cross-block consistency, enabling offline audit and reliable
  joins across tools.

## 2. Artifact Schema Overview

The verifier-carrying artifact is a single JSON object
(`schema_version = "verifier_carrying_artifact.v1"`) intended to be the unit of
exchange for weight-edit evaluation evidence. It is intentionally strict
(`additionalProperties: false`) on core objects so typos and logging drift fail
validation instead of silently passing.

It has three required evidence blocks under a single provenance envelope:

- `provenance`: audit metadata (timestamps, tool versions, optional notes).
- `guard_evidence`: auxiliary evidence from guard frameworks. In v1 this
  includes `guard_evidence.invarlock.evaluation_report` as a hash-linked file
  reference, plus optional `guard_evidence.invarlock.verify` output.
- `verifier_traces[]`: one or more first-class traces of external verifier runs
  (code execution, proof checking, SMT, etc.), each with a determinism-oriented
  contract and per-case verdicts.

The wrapper intentionally treats the InvarLock evaluation report as its own
artifact (referenced by digest), while the verifier trace is the primary
verifier-first outcome record.

## 3. Verifier Trace Contract

The trace contract is the minimal, machine-checkable record binding an external
verifier outcome (e.g., HumanEval pass@1) to the concrete conditions under which
it was produced, so results can be compared and replayed.

The v1 trace records:

- **Verifier identity**: `verifier.name`, `verifier.kind`, and harness identity
  (at least one of version, git commit, or container image digest).
- **Prompt-set integrity**: dataset identifiers plus ordered `(id, sha256)`
  prompt entries and a dataset-level `digest_sha256` computed over canonical
  JSON bytes (UTF-8, sorted keys, compact separators). Two modes are supported:
  `embedded` (text included) and `hash_only` (ids and hashes only) for
  release-safe sharing.
- **Determinism-oriented generation parameters**: model/tokenizer id+revision,
  decoding method and parameters (including seed), and max token limits.
- **Execution sandbox bounds** (for code execution): resource limits and
  explicit `network_enabled=false` (schema-enforced).
- **Results**: per-case verdicts with stable ids and an aggregate summary (e.g.,
  pass@1), optionally with per-attempt outcomes for pass@k.

The contract is a trust boundary: it makes comparability and auditability
machine-checkable, but it does not claim to “prove” determinism across
platforms.

## 4. Schema Verification (Validator)

The `scripts/verifai2_2026/schema_verify.py` tool validates:

1. **Structural conformance** against Draft 2020-12 JSON Schema for both the
   wrapper artifact and each verifier trace.
1. **Cross-block consistency** for contract-defined invariants, including:
   prompt-set digest recomputation, case-id alignment between prompt sets and
   results, and (optionally) on-disk SHA-256 verification when local paths are
   available.

These checks establish evidence integrity and joinability, not correctness.

## 5. Demonstration Corpus and Example Queries

We include a queryable demonstration summary,
`research/verifai2_2026/examples/s1_demo.summary.jsonl`, that illustrates how
verifier-carrying artifacts enable joins and audit queries across tools.

**Demo scope.**

- 11 verifier-carrying artifacts, each paired with 2 verifier traces (HumanEval
  and MBPP), yielding 22 joined rows in the summary.
- 3 base model families: Phi-2, DeepSeek-Coder-1.3B, and Qwen2.5-Coder-3B. Two
  Phi-2 pruning variants are represented as BYOE subject checkpoints.
- Edit families include INT8 RTN quantization recipes and magnitude-pruning
  masks.

### 5.1 Representative Rows

The demo corpus is intentionally small and is not used to claim general
properties of any guard. Its purpose is to make the “joined view” concrete.
Table 1 shows a small sample of rows (one per model family and edit family).

| Model family | Edit | Verifier | Δpass@1 | PM gate | Spec gate | RMT gate | Spectral status |
|---|---|---:|---:|---:|---:|---:|---|
| DeepSeek-Coder-1.3B | INT8 RTN (mild) | HumanEval | +0.012 | ✓ | ✓ | ✓ | capped |
| DeepSeek-Coder-1.3B | INT8 RTN (mild) | MBPP | −0.006 | ✓ | ✓ | ✓ | capped |
| Qwen2.5-Coder-3B | INT8 RTN (mild) | HumanEval | −0.006 | ✓ | ✓ | ✓ | capped |
| Qwen2.5-Coder-3B | INT8 RTN (mild) | MBPP | −0.002 | ✓ | ✓ | ✓ | capped |
| Phi-2 | INT8 RTN (mild) | HumanEval | +0.098 | ✓ | ✓ | ✗ | stable |
| Phi-2 (BYOE) | pruning 40% | HumanEval | +0.220 | ✗ | ✓ | ✓ | stable |

**Note on `spectral_status`.** In InvarLock reporting, `spectral_status="capped"`
means spectral family caps were applied (`caps_applied > 0`); it is not itself
a failure. The gate outcome is recorded separately as `gate_spectral_stable`.

### 5.2 Query Examples

All example queries operate on the JSONL summary and demonstrate patterns that
are hard to see in per-tool logs.

**Q1: “All main gates pass, but the verifier regresses (any amount)”**

```bash
jq -r '
  select(
    .gate_primary_metric_acceptable and
    .gate_invariants_pass and
    .gate_spectral_stable and
    .gate_rmt_stable and
    (.delta_pass_rate < 0)
  )
  | {artifact_path, invarlock_model_id, verifier_name, delta_pass_rate}
' research/verifai2_2026/examples/s1_demo.summary.jsonl
```

This returns small negative deltas for “mild” edits where all gates pass,
illustrating why the trace contract’s `verifier_n_total` is needed to interpret
whether small Δ is meaningful or within binomial noise.

**Q2: “Primary-metric gate fails, yet HumanEval improves materially”**

```bash
jq -r '
  select(
    (not .gate_primary_metric_acceptable) and
    .verifier_name == "humaneval" and
    (.delta_pass_rate >= 0.10)
  )
  | {invarlock_model_id, invarlock_edit_name, delta_pass_rate, primary_metric_ratio_vs_baseline}
' research/verifai2_2026/examples/s1_demo.summary.jsonl
```

These “guard–verifier disagreement” cases are exactly the kind of evidence that
benefits from being packaged and queryable: a verifier-first workflow can
escalate to the external verifier when guard evidence is uncertain or
misaligned.

**Q3: “Which rows fail the spectral gate?”**

```bash
jq -r '
  select(.gate_spectral_stable == false)
  | {invarlock_model_id, verifier_name, spectral_status, spectral_stability_score}
' research/verifai2_2026/examples/s1_demo.summary.jsonl
```

## 6. Limitations

This work standardizes **evidence**, not guarantees. The validator checks
structural well-formedness and contract-driven consistency; it cannot certify
verifier soundness or harness correctness without rerunning the underlying
pipeline.

The demonstration corpus is small and meant to illustrate joins and queries.
Larger-scale analyses of guard–verifier alignment are out of scope here (see
the companion F4 study for that direction).
