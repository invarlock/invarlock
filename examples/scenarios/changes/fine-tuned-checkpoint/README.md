# Evaluate a fine-tuned checkpoint

## When to use this example

Use this recipe after PEFT, TRL, Transformers Trainer, or another training
system has materialized the checkpoint proposed for release. The training
system remains responsible for optimization, checkpoint export, and its own
training records. InvarLock begins with the immutable baseline and fine-tuned
checkpoint.

## Inputs you bring

- Complete local baseline and subject checkpoint trees, including their
  tokenizer files.
- A digest-pinned JSONL evaluation set with stable record IDs and expected
  continuations.
- A policy defining the allowed normalized-NLL regression, minimum record
  count, and interval-width requirement.
- A digest-pinned OCI runtime containing the matching InvarLock and Hugging
  Face stack.
- Evidence and verifier signing identities managed independently.

Use a small schedule only to smoke-test integration. A release qualification
should generally select at least 400 eligible paired records and should encode
both its minimum count and precision requirement in policy.

## InvarLock transaction

Set both request sides to `hf_transformers`, task `text_causal`, metric
`normalized_nll_per_utf8_byte`, and execution mode `run`. The baseline and
subject workers score the same expected continuation for every authenticated
record. The verifier recomputes the normalized-NLL comparison and applies the
policy to the conservative bound.

## What the result establishes

A passing receipt establishes that the exact fine-tuned checkpoint, runtime,
dataset, paired schedule, metric, and policy identities agreed and that the
likelihood-regression bound satisfied the selected release rule.

## Interpretation boundary

Normalized NLL measures expected-continuation likelihood on the selected data.
It is not a general capability score. Training-data quality, safety behavior,
latency, memory use, and application-specific outcomes need appropriate paired
records or separately authenticated observations.

## Run it

Inspect the real CPU request generated by
[`examples/run/hf_cpu_decision.py`](../../../run/hf_cpu_decision.py), then
author the same closed request around the two materialized checkpoints. Run
preflight before allocating model compute:

```console
invarlock evaluate request.yaml --signing-key evidence-signer.pem \
  --runtime-image "$RUNTIME_IMAGE" --runtime-image-digest "$RUNTIME_DIGEST" \
  --runtime-device cuda:0 --preflight
invarlock evaluate request.yaml --signing-key evidence-signer.pem \
  --runtime-image "$RUNTIME_IMAGE" --runtime-image-digest "$RUNTIME_DIGEST" \
  --runtime-device cuda:0
```

Complete the independent `verify` and `report` handoff described in the
[scenario catalog](../../README.md#common-transaction).
